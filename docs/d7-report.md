## 发现

### 发现 1（重要）：长文本要等十几秒才开始出声

1410 字的段落合成用了 12.6s，期间用户只看到「正在合成…」。这是目前唯一会让人以为“卡住了”的场景。

正式版（C#）应改为**分段流水线**：按句子切分，合成第一段后立刻开始播放，其余段落边播边合成。这样首音延迟固定在 1.2–1.8s，与总长度无关。

Python 原型不再改这一点，属于架构级改动，放到 C# 版本做。

### 发现 2：打断必须由新版承担

旧实现用 `_busy` 锁拒绝第二次请求，用户必须先点「停止」。已改为“新请求优先”（提交 `7f510ce`）：停旧音频、作废旧任务、立刻开始新内容。C# 版本从一开始就要按“可抢占”设计，不要引入互斥的播放状态机。

### 发现 3：双击选词是最常用的手势

实际测试里双击选词和拖选都很频繁，且双击时鼠标位移为 0，必须靠点击计数识别。手势判定逻辑（拖选 / 双击 / Shift 点选）在正式版里原样保留。

### 发现 4：失败基本都是“没有选区”

26 次朗读全部成功，5 次取词失败全部是无选区。正式版不需要更复杂的重试，只需要把“没有检测到选中文本”的提示做清楚。

## 对 C# 正式版的要求

必须保留的行为：

1. Win32 `RegisterHotKey` 注册全局热键（不用键盘钩子）。
2. UIA `TextPattern` 优先，`Ctrl+C` 兜底；控制台和文件管理器跳过剪贴板。
3. 无焦点浮窗（`WS_EX_NOACTIVATE`）+ 4 秒自动隐藏。
4. 全屏暂停、进程排除、托盘开关。
5. 新请求抢占旧朗读。

新增/改进：

1. 分段合成 + 流水线播放，首音不随文本变长而变慢。
2. 相同文本的音频缓存（重复划同一句不再请求网络）。
3. 打包为单文件 exe（无控制台窗口）、可选开机自启。
4. 设置界面：音色、语速、排除列表，不用手改 JSON。
5. Azure Speech 作为第二引擎（`engine` 字段已预留）。

技术选型建议：

| 部分 | 建议 |
|---|---|
| UI / 托盘 | WPF 或 WinForms + `NotifyIcon` |
| UIA | `UIAutomationClient` COM 互操作（`System.Windows.Automation`） |
| 热键 / 钩子 | P/Invoke `RegisterHotKey`、`SetWindowsHookEx(WH_MOUSE_LL)` |
| TTS | 直接走 Edge TTS WebSocket 协议（`wss://speech.platform.bing.com/...`），拿到 `audio/*` 分片就写盘/播放 |
| 播放 | NAudio `WaveOutEvent` / `MediaFoundationReader`，支持立即停止 |

## 风险

| 风险 | 影响 | 处理 |
|---|---|---|
| Edge TTS 是非官方接口，可能限流或改协议 | 朗读不可用 | 保留 Azure 引擎开关；正式版加本地 `SAPI` 兜底 |
| 全局鼠标钩子被安全软件/反作弊拦截 | 自动弹窗失效 | 热键始终可用，作为逃生口 |
| 打包 exe 被 SmartScreen/杀软误报 | 无法安装 | 代码签名；首次运行提示 |
| 部分应用（管理员权限、DRM、游戏）取不到词 | 无法朗读 | 文档说明 + 排除列表 |
